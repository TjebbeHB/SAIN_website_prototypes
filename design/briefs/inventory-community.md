## 1. Cross-cutting patterns (read this first)

- **Page shape is identical across all three live chapters**: Hero → (recruiting/hiring banner, conditional) → in-page pill nav (`#events` / `#programs` / `#about` / `#join`) → Events section → Programs section (Courses → Discussion group(s) → Research) → About → Team → Join & contact.
- **Events are NEVER hard-coded as "upcoming" in the chapter page components.** Every chapter page shows:
  1. A live Luma **iframe embed** (`https://luma.com/embed/calendar/<CALENDAR_ID>/events?lt=light`) for "upcoming events" — this is the only place upcoming events appear, and it depends on Luma's calendar content, not on anything in this repo.
  2. A **"past events this academic year" list**, sourced from a static JSON file (`lumaPastEventsAmsterdam.json` / `lumaPastEventsUtrecht.json`) that must be regenerated by hand via the `scripts/fetch-luma-events-*.mjs` scripts. Groningen instead links out to a full separate archive page (see §4) — Groningen has **no** `lumaPastEventsGroningen.json` file inventoried here (none was in the file list).
  - Academic-year cutoff logic (Utrecht & Amsterdam, identical function): `academicYearStart(now)` = Sept 1 of the current or most recent academic year (if month index ≥ 8, i.e. Sept, use this calendar year; else previous year). Only events with `startAt >= academicYearStart(new Date())` are shown, sorted newest first.
  - Date display format: `en-GB`, `{ month: "short", year: "numeric" }` (e.g. "Jun 2026").
- **"Join our community" CTA** on every chapter hero and footer points to `COMMUNITY_JOIN_URL = "https://sainonboard.fillout.com/new"` (from `src/data/siteContact.ts`). This is a single shared onboarding form for all chapters — not chapter-specific.
- **"National newsletter (Substack)" CTA** everywhere points to `https://safeainetherlands.substack.com/` (constant `NATIONAL_SUBSTACK_URL`, redefined per-file rather than imported from a shared module — same value in Utrecht, Groningen, Amsterdam page files).
- **Course application / sign-up**: `COURSE_APPLICATION_URL = "https://sainonboard.fillout.com/t/4fQyZTbTCAus"` — one shared Fillout form for participants AND facilitators, across all three chapters (from `src/data/courseApplications.ts`). Whether the sign-up CTA shows, and what deadline text renders, is driven by `courseApplicationFor(chapterName)`.
- **"We are recruiting / hiring" banner**: driven by `isChapterRecruiting(chapterName)` from `src/data/openPositions.ts`; when true, links to `/open-positions#chapter-<city>`. Copy always uses `APPLICATION_REVIEW.phrase = "on a rolling basis"` (full sentence available: "Applications are reviewed on a rolling basis, so apply whenever you are ready.").
- **Contact emails**: every chapter renders a grid of `mailto:` links, one per role, subject line auto-filled (e.g. `SAIN Utrecht — Events`). The exact same 7 roles recur for every chapter with only the local-part prefix changing: Formal collaboration (`info<xx>@…`), Community Manager (`cm<xx>@…`), Education (`edu<xx>@…`), Research (shared `research@safeainetherlands.org`, not chapter-prefixed), Events (`events<xx>@…`), Substack (shared `substack@safeainetherlands.org`), Public Outreach (`pr<xx>@…`). All addresses are on the `safeainetherlands.org` domain.
- **Icons used** (Phosphor, `@phosphor-icons/react/dist/ssr`, `weight="light"`): `CaretRight` (past-events row chevron), `Check` (highlights/checklist bullets), `GraduationCap` (recruiting banner icon), `ArrowRight` (Groningen "View full Research Hub" link), `Clock` and `MapPin` (in `ChapterPlaceholder`). No hand-drawn SVGs found in these files needing conversion — icons are already Phosphor. The only raw `<img>` (not `next/image`) is the ELLIS logo (`/logos/ellis.svg`) on the Amsterdam page, used twice (hero "Supported by" lockup and the About/Partners card).

## 9. `scripts/fetch-luma-events-amsterdam.mjs` and `scripts/fetch-luma-events-utrecht.mjs`

Both are manual, one-off Node scripts (`npm run fetch-luma-events-amsterdam` / `-utrecht`), **not run at build time**. They:
- Hit `https://api.lu.ma/calendar/get-items?calendar_api_id=<ID>&period=past&pagination_limit=50` for a hard-coded calendar ID.
  - Amsterdam script ID: `cal-WD5xl5IYLpY7xNm` (matches the page's `LUMA_CALENDAR_ID`).
  - Utrecht script ID: `cal-SEgERCbTEKinGaJ` (**does not match** the Utrecht page's `LUMA_CALENDAR_ID` of `cal-2gYun0D26BriJ5z` — flagged above in §2).
- Map each Luma API entry to `{ name, url: "https://lu.ma/" + event.url, startAt: event.start_at }`, sort newest-first.
- Amsterdam script **overwrites** the JSON file outright each run.
- Utrecht script is slightly smarter: it reads the *existing* JSON file first (if present) and merges/preserves entries not present in the fresh API pull (based on comparing `url` sets) — this is presumably how the LinkedIn-post URLs got into the Utrecht past-events file in the first place (someone manually added LinkedIn-post entries to the JSON, and the script preserves them on subsequent runs since they're not in the Luma API response). This explains the mixed URL types noted in §5.
- Both accept an optional `LUMA_API_KEY` env var for authenticated calendars (Utrecht script only; comment says "do not commit secrets").

### Critique — fetch scripts
- The calendar-ID mismatch (Utrecht) should be resolved or explained — right now it looks like a bug/oversight, not a deliberate choice.
- Nothing in the repo currently validates that the two calendar IDs (script vs. page) stay in sync; a silent content-drift risk.
- The Utrecht "merge preserved manual entries" behavior is undocumented as page-facing user behavior — worth a one-line comment explaining why LinkedIn URLs coexist with Luma URLs, since a future dev might otherwise treat it as a bug and "fix" it away.

## 10. Consolidated critique — cross-chapter (for the copywriter & designer)

1. **Events model is genuinely inconsistent across the three live chapters**: Utrecht/Amsterdam show upcoming (Luma embed) + past (JSON list, academic-year filtered) inline; Groningen shows upcoming (Luma embed) only inline, and pushes ALL past events to a separate, hand-maintained TS archive page with no year-based filter tied to "this academic year." A copywriter should decide (and ask the org) whether this is meant to converge to one pattern.
2. **No page currently hard-codes literal "upcoming" event data** — "upcoming" always means "whatever the live Luma iframe shows," which this codebase cannot see or list as text/facts. Any inventory or QA of "what events are upcoming" must be done by checking Luma directly, not the repo.
3. **Contact-email duplication** (chapter page inline arrays vs. `siteContact.ts`'s `chapterRoleEmails`) is a maintenance trap — same 21 email/label pairs (7 roles × 3 chapters) effectively declared twice.
4. Course names, cohort sizes, deadlines, and terminology (Fundamentals vs. Ethics-and-Society vs. Technical-Safety-and-Governance) differ chapter to chapter with no shared vocabulary or cross-links explaining the differences — likely intentional (each chapter picked its own curriculum/provider: ARENA for Utrecht's technical track, Center for AI Safety for Groningen, BlueDot for Amsterdam) but currently unexplained on-page.
5. Heavy acronym/proper-noun load with no glossary: BERI, Pathfinder, ARENA, AGISF, AISIG, AISA, ELLIS, BlueDot, TransformerLens/SAELens/Neuronpedia, GRPO/PPO/RLHF, CAIS ("Center for AI Safety"). Fine for an in-the-know audience; a general visitor gets none of this defined.
6. Visual/component inconsistencies noted throughout (recruiting-banner card style Groningen vs Utrecht/Amsterdam; Utrecht team cards are links, Groningen/Amsterdam team cards are static) will matter to the designer doing a redesign pass — these are not content facts but affect how "the same section" should be templated across chapters.
7. Two verified data-integrity flags worth resolving before/along with the redesign: (a) Utrecht Luma calendar ID mismatch between page and fetch script; (b) Utrecht past-events JSON mixing Luma-event and LinkedIn-post URLs under one "past events" affordance.
